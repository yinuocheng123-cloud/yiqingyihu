# 版本记录：v0.4-回访复购与客户跟进沉淀

## 1. 本轮目标

本轮目标是在“客户建档 -> 订单录入”主链路基础上，继续打通“订单后回访 -> 复购判断 -> 客户详情沉淀”这段业务流程，具体包括：

- 实现回访复购模块
- 支持三次回访录入
- 支持标记复购、会员、代理机会
- 在客户详情中展示跟进沉淀

本轮属于：
- 功能补充
- 业务闭环推进

## 2. 背景与上下文

本轮承接：

- `custom/notes/v0.1-项目初始化与权限骨架.md`
- `custom/notes/v0.2-客户管理首轮落地.md`
- `custom/notes/v0.3-订单管理与客户详情闭环.md`

上一轮已完成客户与订单的最小闭环，但订单之后的跟进还没有落地。没有回访记录，系统仍然无法回答这些关键问题：

- 客户用了没有
- 用得怎么样
- 能不能复购
- 能不能转会员
- 有没有代理意向

## 3. 问题分析

当前核心矛盾不是“回访模块能不能做得很复杂”，而是“成交后的信息如何稳定沉淀为后续动作依据”。

主要问题：

- 成交后缺少结构化回访记录
- 复购机会、会员机会、代理机会没有统一落点
- 客户详情里还看不到真正的售后/回访跟进结果

如果现在再单独做一套“客户跟进表”和一套“回访表”，很容易把模型做散，增加维护成本。

## 4. 候选方案比较

### 方案一：新增独立客户跟进表，再单独做回访表

优点：
- 语义上更细分

缺点：
- 当前阶段模型会变复杂
- 客户跟进和订单回访边界容易混淆
- 会拉高前后端实现成本

放弃原因：
当前 MVP 阶段不适合拆这么细。

### 方案二：先把回访记录作为当前阶段最关键的跟进沉淀

核心思路：
- 回访直接挂在订单和客户之上
- 三次回访与复购判断都统一落在 `followups`
- 客户详情直接展示回访摘要

优点：
- 结构简单
- 与成交链路天然关联
- 能最快支撑复购判断

缺点：
- 当前阶段“跟进记录”语义主要靠回访承载，不够泛化

选择原因：
最符合当前业务优先级和最小可用原则。

## 5. 最终决策

本轮采用“回访即当前阶段核心跟进沉淀”的方案：

- 后端新增回访模块
- 支持新增、查询、编辑回访
- 支持三次回访结果、满意度、预计复购时间、复购/会员/代理机会标记
- 回访保存后自动同步客户与订单上的跟进状态
- 客户详情展示回访摘要

关键取舍：

- 暂不做自动提醒任务
- 暂不做回访模板和自动化流程
- 暂不拆独立“客户跟进日志表”

## 6. 具体实现

主要改动文件：

- 后端
  - `apps/server/src/modules/followups/`
  - `apps/server/src/common/enums/permission.enum.ts`
  - `apps/server/src/app.module.ts`
  - `apps/server/src/modules/customers/customers.service.ts`
  - `apps/server/prisma/seed.ts`

- 前端
  - `apps/web/src/types/followup.ts`
  - `apps/web/src/api/followups.ts`
  - `apps/web/src/pages/followups/FollowupsPage.tsx`
  - `apps/web/src/pages/customers/CustomerDetailPage.tsx`
  - `apps/web/src/types/customer.ts`

实现效果：

- 可以为订单创建回访记录
- 可以录入三次回访时间与结果
- 可以记录满意度和预计复购时间
- 可以标记可复购、已复购、可转会员、代理意向
- 保存回访后会同步更新客户和订单的相关状态
- 客户详情中可以看到回访摘要沉淀

## 7. 本轮优点

- 成交后的跟进不再丢失
- 复购判断第一次有了结构化落点
- 客户详情开始从“静态档案”变成“动态经营视图”
- 为下一轮会员转化、代理筛选、提醒逻辑打下直接基础

## 8. 本轮缺点与代价

- 当前跟进沉淀主要依赖回访表，仍不是完全泛化的客户跟进体系
- 回访详情页还未单独展开
- 还没有做预计复购到期提醒
- 回访结果仍是手工录入，尚未与消息系统或自动化联动

## 9. 验证与结果

本轮已执行：

- `npm run lint -w apps/server`
- `npm run build -w apps/server`
- `npm run lint -w apps/web`
- `npm run build -w apps/web`

结果：

- 前后端类型检查通过
- 前后端构建通过
- 新增回访模块与客户详情联动未引入编译错误

## 10. 本轮结论

对当前阶段来说，先把回访作为成交后的核心跟进沉淀是合理的。它既能承接真实业务，又不会过早把系统做复杂。客户、订单、回访三者连起来之后，系统已经具备了初步的“承接成交并推动复购”的能力。
