# 版本记录：v0.1-项目初始化与权限骨架

## 1. 本轮目标

本轮目标是为“一清一护全球严选 OPC 操作系统”建立首轮可复用基线，完成工程目录、技术骨架、数据库初稿和登录权限最小闭环，为后续客户、订单、回访模块开发提供稳定起点。

本轮属于：
- 功能补充
- 结构搭建
- 可维护性提升

## 2. 背景与上下文

当前仓库为空目录，没有历史代码、没有正式记录、没有现成 Git 仓库，因此本轮以首轮方案建立基线。

已确认约束：
- 只做后台 Web 管理系统
- 第一版以业务跑顺为目标
- 先做轻量业务中台，不做 ERP 和商城化
- 所有记录与说明需使用中文

## 3. 问题分析

当前最大问题不是“某个模块功能不完整”，而是整个项目还没有任何可运行底座。如果先写具体业务页面，后续会出现权限体系不统一、数据模型不稳定、模块边界模糊的问题。

核心矛盾有三点：
- 没有工程骨架，无法稳定扩展
- 没有统一数据模型，后续模块容易返工
- 没有认证权限底座，业务模块无法真实落地

## 4. 候选方案比较

### 方案一：先写静态后台页面

核心思路：优先做前端页面原型，后续再补后端。

优点：
- 短期视觉反馈快

缺点：
- 数据结构和权限边界容易反复改
- 后续接口联调时返工大

放弃原因：
不符合“先把真实业务跑顺”的目标。

### 方案二：先建立完整工程骨架与认证底座

核心思路：先初始化前后端项目、数据库模型、认证与角色权限基础能力，再逐步扩展业务模块。

优点：
- 模块可持续扩展
- 后续客户、订单、回访可以直接接入
- 便于真实业务迁移

缺点：
- 首轮可见业务页面较少
- 需要先投入一定基础设施工作

选择原因：
更符合 MVP 的长期可维护性要求。

## 5. 最终决策

本轮采用“先搭骨架再扩业务”的方案，技术选型为：
- 前端：React + Vite + TypeScript + Ant Design
- 后端：NestJS + Prisma + PostgreSQL
- 鉴权：JWT + RBAC
- 部署：Docker Compose

设计决策：
- 使用 npm workspaces，而不是 pnpm，因为当前环境中 npm 可用、pnpm 未安装，优先减少环境阻力
- 先将数据库模型一次性铺到核心实体层，但功能实现只先落地登录与权限基础
- 保留操作日志和设置模块的数据表，便于后续模块直接接入

## 7. 本轮优点

- 建立了后续迭代统一骨架
- 先把权限模型立住，避免后续模块散乱
- 数据模型围绕客户、订单、回访主链路展开，便于后续直接接业务
- 保留扩展接口位置，后面接企业微信、小程序、淘宝和 AI 时不会推翻结构

## 8. 本轮缺点与代价

- 当前仍属于第一阶段底座，客户、订单、回访等业务模块还未真正实现 CRUD
- 权限现在是基础版，后续还要补菜单权限与更细的数据范围
- Prisma schema 已较完整，但索引和部分唯一约束还会在实际联调中调整

## 9. 验证与结果

本轮已完成以下验证：

- 执行 `npm install`
- 执行 `npm run prisma:generate -w apps/server`
- 执行 `npm run lint -w apps/server`
- 执行 `npm run build -w apps/server`
- 执行 `npm run lint -w apps/web`
- 执行 `npm run build -w apps/web`

验证结果：

- 前后端 TypeScript 类型检查通过
- NestJS 服务端构建通过
- React 前端构建通过
- Prisma Client 生成通过

验证过程中发现的问题：

- 后端初始 `tsconfig` 的 `rootDir` 与 `prisma/seed.ts` 冲突，已修正
- Prisma 服务中原本预留的关闭钩子在当前 Prisma 类型下产生编译错误，已先简化移除，避免影响本轮基线稳定性
- 前端构建时出现较大的 chunk 警告，但不影响当前 MVP 可运行性，后续可通过按路由拆包优化

## 10. 本轮结论

首轮迭代应优先解决“可运行底座”问题，而不是急于铺业务页面。认证、角色、数据模型一旦稳定，后续客户、订单、回访模块推进会顺畅很多。

## 11. 下一轮建议

1. 进入客户管理模块，先完成客户列表、详情、建档和跟进记录
2. 进入订单管理模块，打通客户到订单的最短闭环
3. 在回访模块中建立三次回访与预计复购提醒逻辑
