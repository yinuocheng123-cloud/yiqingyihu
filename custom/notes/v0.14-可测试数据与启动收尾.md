# 版本记录：v0.14-可测试数据与启动收尾

## 1. 本轮目标

本轮目标不是继续扩展功能，而是把系统真正收尾到“下一步直接 `npm run dev` 就能测试”的状态。

重点解决两件事：

- 种子脚本要能稳定读取本地数据库环境
- 初始化后系统里要有可直接测试的演示业务数据

本轮属于：

- 可用性收尾
- 初始化链路修复
- 交付可测试化

## 2. 背景与上下文

本轮承接以下记录：

- `custom/notes/v0.13-快捷延期与物流批量解析.md`
- `custom/notes/v0.8-上线前收尾与初始化可用化.md`

在前面多轮之后，系统本身的功能已经足够测试，但还存在一个实际问题：

- 登录后如果库里没有演示数据，第一次体验会非常空
- `seed.ts` 在直接执行时没有自动加载 `apps/server/.env`

这意味着代码虽然能跑，但“直接测试使用”的最后一步还没有真正完成。

## 3. 问题分析

问题的表面现象有两个：

- 种子命令执行了，但库里业务数据仍然是 0
- 前端虽然能登录，但进入后几乎是空系统

核心矛盾其实是：

- 系统功能已经 ready
- 但初始化体验还没有 ready

对于当前阶段，这不是小问题，因为用户要的是“现在就能试”而不是“再自己慢慢配”。

## 4. 候选方案比较

### 方案一：不补演示数据，只保留 admin 账号

优点：

- 改动最小

缺点：

- 登录后依然空
- 不符合“直接测试使用”的目标

放弃原因：

不满足当前交付目标。

### 方案二：修 seed 环境变量读取，并在空库时自动写入一组演示数据

优点：

- 初始化后立刻能看见客户、订单、发货、回访、待办
- 不会污染已有真实数据

缺点：

- seed 脚本会稍微变复杂一点

最终选择原因：

这是当前阶段最合理的方案，且收益非常直接。

## 5. 最终决策

本轮最终采用方案二，并做了两个关键决策：

1. `seed.ts` 自带本地 `.env` 读取逻辑
2. 演示数据只在业务表为空时自动写入，避免污染真实数据

## 6. 具体实现

本轮主要修改了以下文件：

- `apps/server/prisma/seed.ts`
  - 增加本地 `.env` 加载逻辑
  - 增加演示数据初始化逻辑
  - 演示数据覆盖：
    - 3 个客户
    - 3 个订单
    - 2 个发货记录
    - 3 个回访
    - 1 个会员
    - 1 个伙伴
    - 1 条内容素材
    - 3 条任务

## 7. 本轮优点

- `npm run seed` 和 `npm run db:setup` 的行为更稳定
- 登录后不再是空系统
- 能直接测试客户、订单、发货、回访、会员、伙伴和待办中心
- 演示数据只在空库写入，对真实使用更安全

## 8. 本轮缺点与代价

- 演示数据是固定样例，不是随机数据
- 如果后续想做更复杂的演示数据切换，还需要单独设计
- 当前目录仍然不是 Git 仓库，无法执行你要求的 `git pull`

## 9. 验证与结果

本轮执行了以下验证：

- `npm run seed -w apps/server`
- 库内计数检查
- `npm run dev:web`
- `npm run dev:server`

验证结果：

- 种子脚本执行成功
- 数据库内已存在演示数据：
  - customers: 3
  - orders: 3
  - shipments: 2
  - followups: 3
  - members: 1
  - partners: 1
  - contentAssets: 1
  - tasks: 3
- `npm run dev:web` 未出现立即报错
- `npm run dev:server` 未出现立即报错

补充说明：

- `npm run dev:*` 超时是因为开发服务器本身是常驻进程，不是失败

## 10. 本轮结论

本轮最重要的结论是：

这套系统现在已经从“代码可运行”推进到了“初始化后可直接测试体验”的状态。
