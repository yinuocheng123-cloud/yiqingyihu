# 版本记录：v0.5-会员管理与首页待办可用化

## 1. 本轮目标

本轮目标是在客户、订单、回访三段主链路基础上，继续把系统推进到“个人可直接日常使用”的 MVP 水位，重点包括：

- 落地会员管理模块
- 落地首页真实经营看板
- 落地首页待办提醒
- 修正客户状态联动逻辑，避免数据语义失真

本轮属于：
- 功能补充
- 可用性提升
- 数据一致性修正

## 2. 背景与上下文

本轮承接：

- `custom/notes/v0.1-项目初始化与权限骨架.md`
- `custom/notes/v0.2-客户管理首轮落地.md`
- `custom/notes/v0.3-订单管理与客户详情闭环.md`
- `custom/notes/v0.4-回访复购与客户跟进沉淀.md`

上一轮已经打通客户、订单、回访，但系统还缺两个关键使用条件：

- 高价值客户没有真正沉淀为会员
- 首页没有形成“我今天该做什么”的待办视图

如果没有这两部分，个人运营时仍然需要在多个页面之间反复切换，无法形成真正的日常工作入口。

## 3. 问题分析

主要问题有三点：

- 回访中虽然能标记会员机会，但没有正式会员实体承接
- 首页还只是占位页，没有真实经营数字和提醒
- 客户状态更新中存在语义风险：标记“可转会员”不应直接等同于“已经是会员”

真正的核心矛盾不是功能数量，而是“系统能不能成为日常操作入口”。如果不能打开首页就知道今天该跟谁、该转谁、该看什么数据，那就还不算可用 MVP。

## 4. 候选方案比较

### 方案一：继续先做更多业务模块，再回头补首页和会员

优点：
- 功能数量增长更快

缺点：
- 日常使用体验依旧割裂
- 会员转化链路断裂
- 首页没有运营价值

放弃原因：
不符合“个人直接使用”的目标。

### 方案二：先补会员承接和首页待办

核心思路：
- 把回访中的会员机会变成可实际落地的会员记录
- 把关键待办统一收口到首页
- 修正客户状态更新逻辑，让数据更可信

优点：
- 明显提升实际使用价值
- 让系统更像业务操作台，而不是功能集合
- 后续继续加发货、代理、内容时结构更稳

缺点：
- 会增加首页聚合接口与联动逻辑

选择原因：
最符合当前“一步到位做到可用 MVP”的目标。

## 5. 最终决策

本轮采用“会员模块 + 首页经营看板 + 首页待办提醒 + 数据联动修正”方案。

具体决策：

- 新增 `members` 模块，支持从客户转为会员
- 客户详情页提供“转为会员”入口
- 首页看板改为真实数据，不再展示静态占位
- 首页待办统一收口四类提醒：
  - 待跟进客户
  - 待回访订单
  - 预计复购提醒
  - 待转会员客户
- 修正回访同步逻辑：不再把“会员机会”直接当作“已是会员”
- 修正订单同步逻辑：客户若已是会员，不再被订单刷新误改生命周期

- 客户详情里可以直接转会员
- 首页能看到客户数、已购客户、复购客户、会员人数、订单数、累计成交额等概览
- 首页能看到今日最关键的四类待办

## 7. 本轮优点

- 系统开始具备真实“日常工作台”属性
- 会员转化从标记变成真正实体沉淀
- 首页不再是展示页，而是运营入口
- 数据联动语义更准确，减少后续误判

## 8. 本轮缺点与代价

- 会员详情页还未单独展开
- 首页提醒仍是查询式提醒，未接消息通知或自动推送
- 当前看板还以总览和待办为主，未深入到渠道分布和产品排行
- 前端包体继续增大，后续需要做按路由拆包

## 9. 验证与结果

本轮已执行：

- `npm run lint -w apps/server`
- `npm run build -w apps/server`
- `npm run lint -w apps/web`
- `npm run build -w apps/web`

结果：

- 前后端类型检查通过
- 前后端构建通过
- 会员模块、首页看板、待办提醒与客户详情会员转化功能未引入编译错误

## 10. 本轮结论

到这一轮为止，这套系统已经不再只是“模块原型集合”，而是具备了个人可直接使用的 MVP 形态。客户、订单、回访、会员、首页待办已经形成最核心的一条经营链路。
