# 版本记录：v0.2-客户管理首轮落地

## 1. 本轮目标

本轮目标是在 `v0.1-项目初始化与权限骨架` 的基础上，落地第一个真实业务模块“客户管理”，至少实现：

- 客户列表
- 关键字段搜索
- 新增客户建档
- 后端客户 CRUD 基础接口

本轮属于：
- 功能补充
- MVP 主链路推进

## 2. 背景与上下文

本轮承接：
- `custom/notes/v0.1-项目初始化与权限骨架.md`

上一轮已经完成：
- 工程骨架
- Prisma 核心数据模型
- 登录认证
- 角色权限底座
- 后台主布局

当前最应该继续推进的模块是客户管理，因为“客户跟不住”是业务第一痛点，客户模块也是订单、回访、会员、代理转化的上游入口。

## 3. 问题分析

如果继续只做骨架，不落地首个业务模块，系统仍然无法承接真实业务。客户管理是最适合先落地的模块，原因有三点：

- 所有业务流程都从客户开始
- 字段和状态边界已经相对明确
- 它能为订单和回访模块提供真实关联对象

本轮核心矛盾不是“客户模块要做多复杂”，而是“如何在不做过度设计的情况下，先把第一版最常用动作做出来”。

## 4. 候选方案比较

### 方案一：一次性把客户详情、标签、导入导出、跟进记录全部做完

优点：
- 功能更完整

缺点：
- 一轮改动过大
- 容易把客户模块做成小型 CRM
- 会拖慢订单和回访模块推进

放弃原因：
超出当前 MVP 节奏。

### 方案二：先做客户最小闭环

核心思路：
- 先实现列表、搜索、建档和编辑基础
- 详情、标签、跟进记录、提醒后续逐步追加

优点：
- 更符合最小可用原则
- 能尽快与订单模块对接
- 业务价值直接

缺点：
- 当前仍不算客户模块最终形态

选择原因：
更适合当前阶段快速推进真实业务。

## 5. 最终决策

本轮采用“客户模块最小闭环”方案：

- 后端提供 `GET /customers`、`GET /customers/:id`、`POST /customers`、`PATCH /customers/:id`
- 前端提供客户列表、关键字搜索、新增客户抽屉表单
- 数据字段优先保留真实业务高频项：来源、客户类型、生命周期、跟进状态、代理意向、备注

关键取舍：
- 先不做复杂标签体系
- 先不做导入导出
- 先不做客户详情独立页
- 先不做自动提醒任务

## 7. 本轮优点

- 系统从“只有底座”推进到“已有真实业务模块”
- 客户模块可以直接作为订单模块上游
- 字段设计已贴近当前业务场景，而不是泛化成复杂 CRM
- 前后端都保持了清晰分层，后续继续扩展比较顺手

## 8. 本轮缺点与代价

- 客户详情页还未落地
- 客户标签、跟进记录、操作日志关联还未接上
- 当前客户编号生成规则是基于时间戳的简化方案，后续可换成更规范的序列策略
- 搜索和列表仍是最小版，尚未支持复杂筛选、分页和导出

## 9. 验证与结果

本轮验证：

- `npm run lint -w apps/server`
- `npm run build -w apps/server`
- `npm run lint -w apps/web`
- `npm run build -w apps/web`

结果：

- 前后端编译均通过
- 客户模块新增代码未引入新的类型错误
- 前端仍有 chunk 偏大警告，但不影响当前版本运行

## 10. 本轮结论

客户管理模块适合作为第一批业务落地入口。当前最优推进方式不是一次把客户模块做成完整版，而是先打通“建档 + 查询”最小闭环，再快速接订单和回访模块。

1. 继续实现订单管理模块，并与客户建立真实关联
2. 在客户详情中补历史订单、回访记录和操作日志
3. 在回访模块中建立三次回访与预计复购时间的基础能力
