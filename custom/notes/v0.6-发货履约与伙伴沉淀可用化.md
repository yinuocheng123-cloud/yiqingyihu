# 版本记录：v0.6-发货履约与伙伴沉淀可用化

## 1. 本轮目标

本轮目标是在“客户、订单、回访、会员、首页待办”已可用的基础上，继续把系统推进到更适合个人日常使用的状态，重点包括：

- 补齐发货记录与物流单号
- 在订单详情内完成履约跟踪
- 落地伙伴管理模块
- 支持从客户转为伙伴

本轮属于：
- 功能补充
- 可用性提升
- 业务资产沉淀

## 2. 背景与上下文

本轮承接：

- `custom/notes/v0.1-项目初始化与权限骨架.md`
- `custom/notes/v0.2-客户管理首轮落地.md`
- `custom/notes/v0.3-订单管理与客户详情闭环.md`
- `custom/notes/v0.4-回访复购与客户跟进沉淀.md`
- `custom/notes/v0.5-会员管理与首页待办可用化.md`

当前系统虽然已经能承接客户、订单、回访和会员，但仍缺两类高频实际动作：

- 订单发货后没有地方记录物流信息
- 客户代理意向无法正式沉淀成伙伴档案

如果这两块缺失，个人使用时仍然要靠微信或表格补记录，系统闭环会断掉。

## 3. 问题分析

当前主要问题：

- 订单虽然有发货状态字段，但没有真实发货记录
- 无法记录物流公司、单号、发货时间、签收时间
- 代理意向只是客户上的布尔状态，无法形成真正的伙伴档案

核心矛盾不是“功能有没有”，而是“能不能把高频业务动作真正收回系统里”。

## 4. 候选方案比较

### 方案一：单独增加发货管理页和伙伴详情页，一次做全

优点：
- 结构更完整

缺点：
- 本轮改动面会明显扩大
- 对 MVP 现阶段来说，页面数量和维护成本都会增加

放弃原因：
当前更重要的是把高频动作嵌回已有流程，而不是铺更多独立页面。

### 方案二：把发货管理嵌入订单详情，把伙伴沉淀做成列表 + 转化入口

核心思路：
- 发货记录直接挂在订单详情页
- 伙伴先做列表与新增，不急于独立详情页
- 客户详情提供“转为伙伴”入口

优点：
- 操作路径更短
- 更适合个人使用
- 最小改动即可明显提升可用性

缺点：
- 后续如果伙伴流程变复杂，仍可能需要独立详情页

选择原因：
最适合当前阶段“一步到位做到可直接使用”的目标。

## 5. 最终决策

本轮采用“订单详情内嵌发货管理 + 伙伴列表化沉淀”方案。

具体决策：

- 后端新增 `shipments` 模块
- 发货记录新增/编辑时自动同步订单发货状态、签收状态、发货时间、签收时间
- 前端在订单详情页中直接维护发货记录
- 后端新增 `partners` 模块
- 前端新增伙伴管理页面
- 客户详情支持直接转为伙伴

## 6. 具体实现

主要改动文件：

- 后端
  - `apps/server/src/modules/shipments/`
  - `apps/server/src/modules/partners/`
  - `apps/server/src/common/enums/permission.enum.ts`
  - `apps/server/prisma/seed.ts`
  - `apps/server/src/app.module.ts`

- 前端
  - `apps/web/src/types/shipment.ts`
  - `apps/web/src/types/partner.ts`
  - `apps/web/src/api/shipments.ts`
  - `apps/web/src/api/partners.ts`
  - `apps/web/src/pages/orders/OrderDetailPage.tsx`
  - `apps/web/src/pages/partners/PartnersPage.tsx`
  - `apps/web/src/pages/customers/CustomerDetailPage.tsx`
  - `apps/web/src/types/order.ts`

实现效果：

- 可以在订单详情中新增发货记录
- 可以填写物流公司、物流单号、发货/签收时间
- 可以编辑已有发货记录
- 发货记录会同步订单状态
- 可以新增伙伴档案
- 可以从客户详情直接转为伙伴

## 7. 本轮优点

- 订单履约链路从状态字段升级为真实记录
- 高价值客户的代理意向开始沉淀为结构化伙伴资产
- 操作入口放在最贴近业务动作的页面里，使用成本更低
- 系统更接近个人日常运营场景，而不是纯管理展示

## 8. 本轮缺点与代价

- 发货仍未单独形成列表页和异常处理流
- 伙伴模块当前还没有独立详情页和培训历史明细
- 物流状态仍是手工维护，未接第三方物流接口
- 首页还没有把发货待办单独收口

## 9. 验证与结果

本轮已执行：

- `npm run lint -w apps/server`
- `npm run build -w apps/server`
- `npm run lint -w apps/web`
- `npm run build -w apps/web`

结果：

- 前后端类型检查通过
- 前后端构建通过
- 发货履约与伙伴沉淀相关功能未引入编译错误

## 10. 本轮结论

到这一轮为止，系统的 MVP 主链路已经更完整了：客户、订单、回访、会员、伙伴、首页待办和发货履约都已有可操作入口。对个人使用来说，这已经是一套能够承接真实业务的轻量后台。

## 11. 下一轮建议

1. 增加内容素材模块，把客户原话、回访反馈和售后问题沉淀成内容库
2. 增加系统设置中的来源渠道、客户类型、产品类别与枚举配置
