# 版本记录：v0.16-任务默认指派与优先级筛选

## 1. 本轮目标

本轮目标是在上一轮“首页负责人视角 + 优先级快捷调整”的基础上，继续压缩日常处理路径。

优先解决两件事：

- 新任务虽然能自动生成，但很多仍然是未指派状态，登录后还要再手工领取
- 待办中心虽然已经支持人工调整优先级，但还不能直接按优先级筛选

本轮属于：

- 功能补充
- 使用效率提升
- 可维护性增强

## 2. 背景与上下文

本轮承接以下记录：

- `custom/notes/v0.15-首页负责人视角与任务优先级增强.md`
- `custom/notes/v0.14-可测试数据与启动收尾.md`

`v0.15` 已经明确，当前阶段继续做“高频动作压缩”比继续铺新模块更有价值。

上一轮结论里最值得继续推进的两件事就是：

1. 增加任务默认指派策略
2. 增加任务优先级筛选和排序控制

本轮完全延续这条思路，没有改数据库结构，也没有引入新的任务表或规则表。

## 3. 问题分析

表面现象：

- 自动生成的任务很多默认是“未指派”
- 待办中心里虽然能看到优先级列，但无法直接筛出 `P1` 或 `P2`

核心矛盾：

- 系统已经具备自动化雏形
- 但“自动推进到谁手里”和“快速筛出最急任务”这两步还不够顺

如果默认指派缺失，任务中心仍然会有一堆待领取项，需要人工二次分发。
如果优先级不能筛选，优先级字段就更多只是展示，而不是实际操作工具。

## 4. 候选方案比较

### 方案一：只做优先级筛选，不做默认指派

核心思路：

- 前端增加优先级下拉
- 后端任务查询支持 priority

优点：

- 改动最小
- 风险最低

缺点：

- 只能改善“找任务”的效率
- 不能改善“任务落到谁手里”的问题

放弃原因：

收益不完整，没有覆盖当前最明显的人工动作。

### 方案二：增加轻量默认指派策略，并补优先级筛选

核心思路：

- 在 `ensureTask` 中统一做默认负责人解析
- 优先复用已有业务字段：
  - 客户任务 -> `customer.ownerId`
  - 发货任务 -> `order.shipmentOwnerId`
  - 其他订单任务 -> `customer.ownerId`
  - 回访/复购/会员/伙伴任务 -> `followup.responsibleId`，其次 `customer.ownerId`
- 同时让待办中心支持按优先级筛选

优点：

- 不改表结构
- 不需要在每个业务模块里重复写默认指派逻辑
- 让任务生成和待办处理形成更顺的闭环

缺点：

- 默认指派规则暂时还是写在代码里
- 某些特殊业务场景可能仍然需要人工改派

最终选择原因：

这条路径成本低、收益高，而且和现有任务中心结构最兼容。

## 5. 最终决策

本轮最终采用方案二，并做了两个关键决策：

1. 默认指派规则先集中放在 `TasksService.ensureTask`
2. 优先级筛选先做精确值筛选，不额外引入复杂排序配置

这样做的原因是：

- 避免把默认指派逻辑散落在客户、订单、发货、回访多个模块里
- 先把最常用的筛选能力做稳，再决定是否继续扩展更复杂的优先级视图

## 6. 具体实现

本轮主要修改了以下文件：

- `apps/server/src/modules/tasks/dto/query-tasks.dto.ts`
  - 增加 `priority` 查询参数校验

- `apps/server/src/modules/tasks/tasks.service.ts`
  - `findInbox` 支持按优先级筛选
  - `ensureTask` 在没有显式 `responsibleId` 时，会自动解析默认负责人
  - 默认指派规则优先沿用已有业务负责人字段，避免额外建规则表

- `apps/web/src/api/tasks.ts`
  - 前端任务查询接口增加 `priority` 参数

- `apps/web/src/pages/tasks/TasksPage.tsx`
  - 待办中心增加“按优先级筛选”
  - 保留上一轮的优先级快捷调整能力

## 7. 本轮优点

当前方案相比之前的提升主要体现在：

- 新生成任务更容易自动落到正确负责人手里
- 待办中心可以直接筛出 `P1`、`P2` 等高优先级任务
- 默认指派逻辑集中，后续更容易继续扩展
- 没有引入新的持久化结构，保持了 MVP 的轻量性

改善的质量属性包括：

- 可用性
- 可维护性
- 操作效率
- 一致性

## 8. 本轮缺点与代价

当前方案也有明确局限：

- 默认指派是静态代码规则，还不是后台可配置策略
- 订单类任务目前优先依赖客户负责人和发货责任人，尚未覆盖更细的角色路由
- 优先级筛选目前是单值筛选，不支持多选或区间筛选
- 当前目录依旧不是 Git 仓库，无法执行你要求的 `git pull`

这些取舍是当前阶段可以接受的，因为本轮目标是把处理链路继续压短，而不是上来就做复杂任务调度系统。

## 10. 本轮结论

本轮最重要的结论是：

任务中心要继续像“操作台”靠拢，下一步最有效的不是堆更多任务类型，而是减少任务生成后还要再分发、再筛选的人工步骤。

被证实的判断有两个：

- 默认指派确实应该集中在任务创建入口统一处理
- 优先级只有能筛选，才算真正进入日常操作链路

以后应默认继承的经验是：

- 能从已有业务负责人字段推导的任务，优先自动指派
- 待办中心的增强优先围绕“少找、少点、少改派”

## 11. 下一轮建议

下一步最值得做的 1~3 件事：

1. 增加任务自动关闭/自动降级策略
   - 收益最高
   - 比如某些已过期低优先级任务自动提醒或降级处理

2. 增加首页“仅看我的 P1/P2”快捷入口
   - 风险最低
   - 能进一步缩短每天进入系统后的判断路径

3. 增加消息提醒入口
   - 需要更多信息后再做
   - 适合后续和企业微信、站内提醒或短信结合
