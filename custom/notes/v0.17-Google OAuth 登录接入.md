# 版本记录：v0.17-Google OAuth 登录接入

## 1. 本轮目标

本轮目标是为系统接入 Google OAuth 登录，作为现有账号密码登录的替代入口之一，并保持现有登录方式不被破坏。

优先解决的问题：

- 现有登录只有本地账号密码，不够方便
- 用户明确要求接 Google OAuth

本轮属于：

- 功能补充
- 登录体验提升
- 可维护性增强

## 2. 背景与上下文

本轮承接以下记录：

- `custom/notes/v0.16-任务默认指派与优先级筛选.md`

当前系统在改动前的状态是：

- 后端认证完全基于本地用户表 + JWT
- 前端登录页只有账号密码表单
- 尚未接入任何第三方身份提供方

已知约束：

- 当前项目是 MVP，优先做最小可落地实现
- 不希望为接入 OAuth 额外引入过多新依赖
- 仍需保留本地账号密码登录作为兜底入口

## 3. 问题分析

表面现象：

- 登录方式单一
- 外部身份接入能力为空白

核心矛盾：

- 用户想要更方便的第三方登录
- 但系统当前没有 OAuth 回调、用户映射和前端回跳处理链路

真正要解决的不是“加一个按钮”，而是打通这条链：

- 前端发起授权
- Google 回调到后端
- 后端换取用户信息
- 本地生成/映射用户
- 签发系统 JWT
- 前端接收并写入登录态

## 4. 候选方案比较

### 方案一：使用 Passport Google Strategy

核心思路：

- 安装 `passport-google-oauth20`
- 按 Nest 常见 Passport 策略方式接入

优点：

- 社区方案成熟
- 文档较多

缺点：

- 需要新增依赖
- 对当前 MVP 来说，依赖和样板代码都会增加

放弃原因：

当前项目已经有 JWT 和基础认证链路，直接走标准 OAuth HTTP 交换更轻。

### 方案二：直接按 Google 官方 OAuth 标准流程实现

核心思路：

- 后端生成 Google 授权地址
- 回调时用标准 token endpoint 换 `access_token`
- 再通过 `userinfo` 获取用户资料
- 将 Google 用户映射到本地用户后签发 JWT

优点：

- 不新增第三方 OAuth 依赖
- 与当前项目结构更贴合
- 更容易控制回跳逻辑

缺点：

- 需要自己处理状态参数和用户映射逻辑
- 需要更仔细做回调容错

最终选择原因：

在当前项目规模下，这是更轻、更稳、更容易维护的做法。

## 5. 最终决策

本轮最终采用方案二，并做了几个关键决策：

1. 保留账号密码登录，不强行替换
2. Google OAuth 成功后仍统一换成系统自己的 JWT
3. 不修改用户表结构，优先用 Google 邮箱映射到 `username`
4. 新建 Google 用户时，默认赋予 `OPERATOR` 角色

这样设计的原因：

- 保持系统认证出口统一，后续权限判断不用区分登录来源
- 不引入数据库结构变更，减少风险
- 保留本地登录，避免 Google 配置不完整时系统不可用

## 6. 具体实现

本轮主要修改了以下文件：

- `apps/server/src/modules/auth/auth.controller.ts`
  - 新增 `/auth/google`
  - 新增 `/auth/google/callback`

- `apps/server/src/modules/auth/auth.service.ts`
  - 新增 Google 授权地址生成
  - 新增回调换 token 和 userinfo 获取逻辑
  - 新增 Google 用户到本地用户的创建/映射逻辑

- `apps/server/.env.example`
  - 新增：
    - `GOOGLE_CLIENT_ID`
    - `GOOGLE_CLIENT_SECRET`

- `apps/web/src/api/auth.ts`
  - 新增 `getGoogleLoginUrl`

- `apps/web/src/router/index.tsx`
  - 新增前端回调路由 `/auth/google/callback`

- `apps/web/src/pages/auth/GoogleAuthCallbackPage.tsx`
  - 新增 Google 回调落地页

- `apps/web/src/pages/auth/LoginPage.tsx`
  - 保留账号密码登录
  - 新增 Google 登录按钮
  - 新增 Google 登录失败提示

## 7. 本轮优点

相比之前，本轮的正向效果主要有：

- 系统具备了第三方登录扩展能力
- 登录来源统一回到系统 JWT，不破坏现有权限体系
- 没有引入新的 OAuth 依赖，项目复杂度控制得住
- 前端和后端回跳链路完整，后续接其他 OAuth 提供方也更容易复用

改善的质量属性包括：

- 可用性
- 可扩展性
- 可维护性

## 8. 本轮缺点与代价

这轮也有明确局限：

- 当前无法在没有真实 Google Client ID / Secret 的前提下完成完整授权实测
- 用户表目前没有单独 email 字段，Google 身份映射依赖 `username`
- 新建 Google 用户默认给 `OPERATOR`，这是一种 MVP 阶段的保守默认值，后续可能要改成可配置
- 当前目录虽然现在已经是 Git 仓库，但本轮未做额外推送动作

这些代价当前是可接受的，因为重点是先把 OAuth 主链路打通。

本轮执行了以下验证：

- `npm run lint -w apps/server`
- `npm run build -w apps/server`

验证结果：

- 代码类型检查通过
- 前后端构建通过
- Google 授权入口 URL 生成正确

未完成验证：

- 无法完成真实 Google 授权登录

原因：

- 当前本地尚未提供真实的 `GOOGLE_CLIENT_ID`、`GOOGLE_CLIENT_SECRET`
- Google 控制台中的回调地址也还未由你确认配置

## 10. 本轮结论

本轮最重要的结论是：

Google OAuth 已经从“无能力”推进到“链路代码完成、等待真实配置”的状态。

被证实的判断：

- 对当前项目而言，直接走 Google 官方 OAuth 标准流程比引入额外 Passport 策略更合适
- 保留本地账号密码登录作为兜底是正确的

以后应默认继承的经验：

- 第三方登录统一换发系统 JWT
- 外部身份只负责认证，不直接替代系统内部权限模型

## 11. 下一轮建议

下一步最值得做的 1~3 件事：

1. 配好真实 Google OAuth 凭证并完成联调
   - 收益最高
   - 这是把当前接入从“代码完成”推进到“真实可用”的关键一步

2. 增加 Google 登录用户的后台可见标识
   - 风险最低
   - 方便后续区分账号来源

3. 为企业微信或其他 OAuth 提供方抽象复用入口
   - 需要更多信息后再做
   - 适合在 Google OAuth 稳定后推进
